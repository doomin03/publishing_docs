# 정본 우선순위 — 목업과 Figma 가 함께 있을 때

앱·웹 공통이다. 근거가 있는 것은 출처를 달고, 없는 것은 「사용자 결정 필요」로 둔다.

## 근거가 있는 우선순위

| # | 어긋남 | 따르는 쪽 | 출처 |
|---|---|---|---|
| 1 | 화면 **구조**(요소 유무·순서·흐름)가 디자인과 화면 설계서 사이에 다르다 | 화면 설계서. 디자인이 다르면 퍼블이 아니라 기획 변경이다 — 멈추고 보고한다 | `style-workflow` §0·§5-4 |
| 2 | 비주얼 값이 커밋된 토큰 파일과 Figma MCP 응답 사이에 다르다 | 커밋된 토큰 파일. MCP 는 그 파일을 갱신하는 생산자 중 하나다 | `style-workflow` §6 |
| 3 | 목업 문구가 정책·기능 정본과 다르다 | 정책 정본. 멈추고 적는다 | `PUB-FLOW` §5 |
| 4 | 정지 스냅샷과 살아 있는 목업의 상태·동작이 다르다 | 살아 있는 목업 | `PUBLISHING` §3, `PUB-STATES` 서두 |
| 5 | 문서의 문장(「카드는 불투명」 등)과 테마가 켜진 계산값이 다르다 | 계산값 | `TRAPS` §21 |
| 6 | 스냅샷과 오너 판정이 다르다 | 오너 판정. 스냅샷을 근거로 되돌리지 않는다 | `PUB-FLOW` §4-9 |

- Figma 를 읽을 수 없으면 캐시와 화면 설계서로 진행하고
  리포트에 「Figma 스펙 미확인」을 쓴다. 간격·색을 추측해 확정으로 쓰지 않는다(`style-workflow` §3-1).
- SportLog 의 「Figma 적용 시트」는 Figma 결과를 HTML 목업 위에 CSS 로 덮은 것이었다(`design-4.0`).
  이 경우 HTML 계산값 스펙에는 Figma 적용 결과가 이미 들어 있다 — **추정**(스펙이 시트 적용 뒤 렌더라는 점에서).

## 사용자 결정 필요 (TODO)

근거 문서가 이 경우를 다루지 않는다. 프로젝트마다 사람이 정하고 출처를 적어 넣는다.

- [ ] D1. 같은 화면에 HTML 목업과 Figma 파일이 **따로** 있고 비주얼 값(색·간격·타이포)이 다를 때 어느 쪽이 정본인가.
- [ ] D2. 속성별로 나누는가 — 예: 구조·문구는 HTML, 비주얼은 Figma. 나눈다면 그 표.
- [ ] D3. 한쪽에만 있는 상태·상세는 그쪽을 정본으로 삼는가, 빈칸으로 보고하는가.
- [ ] D4. Figma 의 어느 페이지·프레임·버전이 정본인가. 「최신」을 무엇으로 아는가.
- [ ] D5. Figma 값이 기존 토큰과 다를 때 토큰을 더하는가, 가까운 토큰을 쓰는가, 묻는가
      (SportLog 안에서도 두 문서가 반대였다 — `common/tokens.md`).
- [ ] D6. 어긋남을 누가 판정하고, 판정 결과를 어디에 남기는가.

## 판단하지 못하면

- 위 표에 해당하지 않거나 D1~D6 이 비어 있으면 **고치지 말고 묻는다.**
- 물을 때 `checklist.md` 의 어긋남 표 한 줄을 채워 보여 준다.
- 사람이 정한 결과는 이 파일의 해당 TODO 에 결정과 날짜를 적어 닫는다.
