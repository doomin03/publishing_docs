# 입력: Figma

앱·웹 공통이다. 플랫폼별 옮기는 법은 `app/`·`web/` 에 있다.
근거는 SportLog `style-workflow` 하나뿐이고 그마저 2026-07 작성이다. 나머지는 TODO 로 둔다.

## 먼저 알아 둘 것

- 「Figma 적용 시트」라는 말이 두 뜻으로 쓰인다.
  - (가) HTML 목업 위에 Figma 결과를 CSS 로 덮은 시트 — 입력은 HTML 이다. `mockup/html-input.md` 의 같은 절.
  - (나) Figma 계정의 좌석(seat) 종류 — MCP 호출 한도를 정한다. 아래 「호출 한도」.
- 한 화면에 HTML 목업도 있으면 `common/source-precedence.md` 를 먼저 적용한다.

## 정본 — 근거 있는 것

- 구조(요소 유무·순서·흐름)의 정본은 화면 설계서다. Figma 가 다른 구조를 그렸으면 기획 변경이다 —
  고치지 말고 보고한다(`style-workflow` §0).
- 비주얼의 정본은 Figma 에서 내보내 **커밋한 토큰 파일**이다. MCP 는 그 파일을 갱신하는 생산자 중 하나다(`style-workflow` §0·§6).
- 디자이너가 플러그인으로 토큰을 내보내는 경로가 비용·재현성 면에서 기본 경로였다(`style-workflow` §6).

## 호출 한도 — 캐시가 먼저다

- MCP 호출 한도가 실제 제약이다. 캐시 없이 재실행하면 예산이 하루에 날아간다(`style-workflow` §3-1).
- 한도는 좌석 종류에 따라 크게 다르다. 수치는 Figma 공식 문서가 정본이고 바뀔 수 있다 —
  설정/환경에 따라 다름(`style-workflow` §6 에 2026-07 시점 표가 있다).
- 노드별 스펙·스크린샷을 캐시에 넣고, 캐시가 빈 때만 MCP 를 부른다(`style-workflow` §3-1).
- MCP 를 못 쓰면 캐시 + 화면 설계서로 진행하고 리포트에 **「Figma 스펙 미확인」**을 쓴다.
  간격·색을 추측해 확정으로 쓰지 않는다(`style-workflow` §3-1).

## Figma MCP 로 읽을 것 — 뼈대

- 이 환경에서는 `get_design_context` 를 부르기 전에 `figma:figma-design-to-code` 스킬을 먼저 로드해야 한다
  (그 스킬의 설명이 MUST 로 요구한다). 모션은 `figma:figma-implement-motion`.
- 읽어 낼 것은 `common/reading-mockups.md` 의 「반드시 읽는 것」과 같다 — 구조·문구·치수와 색·상태·애니메이션.
- 값은 Figma 변수(토큰) 이름으로 받는다. 이름 없이 값만 온 것은 「토큰 없음」 후보로 모은다(`common/tokens.md`).
